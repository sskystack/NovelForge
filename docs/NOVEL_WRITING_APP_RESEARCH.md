# GitHub 小说写作工具调研与 NovelForge 借鉴建议

> 调研时间：2026-11-20。GitHub 数据可能随时间变化，以仓库公开页面为准。

## 1. 调研结论

NovelForge 的定位比大多数开源小说工具更接近“带审计与版本机制的创作操作系统”：项目、正典、人物状态、章节、检索、AI 草稿和作者审批已有独立领域模型。竞品调研中最值得借鉴的是成熟工具的信息架构，以及新工具对“草稿、正史、记忆、审核”的流程化表达。

最重要的三个设计方向：

1. **新建项目必须是产品化引导流程**，不能从空白项目直接堆出人物、大纲和章节表单。
2. **每个 AI 动作都必须可预览、可解释、可撤销**，并明确区分草稿、建议、已批准正典和正式章节。
3. **章节工作台应兼顾“写作”和“决策”**：左侧结构、中央稿纸、右侧相关设定与 AI 助手，但不能让正典检索和聊天淹没正文。

## 2. 借鉴优先级最高的产品

### novelWriter：结构化纯文本与稳健的项目格式

仓库：<https://github.com/saga-soft/novelWriter>

公开状态：约 3.2k Stars；GPLv3；Python/PyQt6；桌面端，支持 Linux、Windows、macOS。

它把小说拆成多个较小文本单体，并用人类可读的纯文本、注释、摘要和交叉引用组织项目。项目格式适合版本控制和文件同步。

**可借鉴：**

- 项目既可视为数据库，也应保留可读、可导出的文件语义。
- 使用轻量结构标记表达章节摘要、注释和交叉引用，而不是把所有元数据藏在二进制格式中。
- 文件夹树、章节节点和场景节点应稳定、有明确层级，便于批量整理和导出。
- 导出与备份是核心工作流，而不是附属功能。

**不建议照搬：**

- 为兼顾纯文本而牺牲结构化人物状态、关系有效区间、来源版本等核心能力。
- 在 UI 中暴露过多自定义标记语法。

**NovelForge 落地点：**

- 完善 [docs/DATABASE.md](DATABASE.md) 对应的导出格式，并保证 Markdown/JSON 工程包可读。
- 在章节列表中加入摘要、状态、字数和下一步建议，形成更高密度的导航。
- 为正典提供“可读工程视图”和“结构化数据视图”的切换。

### Manuskript：从一句 premise 到角色、情节、大纲、世界

仓库：<https://github.com/olivierkes/manuskript>

公开状态：约 2.5k Stars；GPLv3；Python/PyQt5；桌面端，支持 Linux、Windows 和 macOS。

核心流程包括 premise 的逐级展开、人物、情节、索引卡/大纲、世界、物品、情节线、故事线、全屏写作、导入导出、频率分析和自动保存。

**可借鉴：**

- “一句话 premise → 段落摘要 → 完整概要”的渐进式建项目流程。
- 人物、情节、世界、物品、章节和场景使用相同项目下的实体导航。
- 同时提供大纲模式、索引卡和文本写作模式，而不是强制一种视图。
- 注意力模式、故事线、章节字数和段落节奏等提供辅助，不改变正文数据。
- 导入、导出、拼写、频率分析等成熟工具可直接成为日常桌面体验的一部分。

**不建议照搬：**

- 人物模型过浅；NovelForge 应保留人物状态快照、关系区间和证据来源。
- 将写作辅助与正史信息混为一体。

**NovelForge 落地点：**

- 新建小说向导可分为：定位、角色、世界、章节骨架、首章草稿。
- 增加项目概览页，显示 premise、主线、人物、伏笔、下一章和近期变更。
- 在大纲节点中加入目标、冲突、爽点/悬念、伏笔和预计章节区间。

### bibisco：以人物复杂性和叙事结构驱动小说设计

仓库：<https://github.com/andreafeccomandi/bibisco>

公开状态：约 776 Stars；GPLv3；JavaScript；社区版和支持者版。

它强调人物动机、人物内在矛盾、fabula、叙事线、时空社会背景，并将章节与场景、修订、导出组织在一起。

**可借鉴：**

- 人物档案不只记录外貌和身份，还应记录欲望、恐惧、矛盾、秘密、成长和压力。
- fabula 与 disnarration 分离：作者可以维护真实事件时间、叙述揭示顺序和读者已知信息。
- 社会、地理、时间背景应作为可检索正典，而非散落在备注中。
- 场景列表和叙事线可以帮助识别“这章解决了什么”和“读者此刻知道什么”。

**不建议照搬：**

- 提供大量问卷但缺少随用而来的“下一步操作”。
- 只允许人物采用静态档案，无法表达故事时间中的人物状态变化。

**NovelForge 落地点：**

- 人物正典增加“目标、动机、恐惧、秘密、对外形象、内在矛盾、story-time 变化”。
- 增加叙事线和场景目标字段，并与伏笔状态、人物状态关联。
- 将人物访谈转换成结构化草稿，显示待确认字段，而不是直接写成正典。

## 3. 新一代本地 AI 小说应用的可用思路

### Hurricane NovelWriter：世界模型、Studio/Atlas 和按章审计

仓库：<https://github.com/Hurricane0698/novelwriter>

公开状态：约 312 Stars；MIT；FastAPI、SQLite/PostgreSQL、React、桌面版。

其核心是把人物、关系、体系、事实和伏笔组织成世界模型；续写时只注入当前章节真正需要的设定；设定变化必须由作者逐条审核。

**可借鉴：**

- 用“工作区”和“正典工作台”分区：Studio 写正文，Atlas 管实体、关系和审核。
- 每次续写只构造章节相关上下文，并让用户知道注入了哪些实体和来源。
- “本章改变了什么？”可以把正文提取为人物状态、关系、事件和伏笔建议。
- AI 建议同时保留原值、新值、证据章节和置信度，方便逐条比较。

**NovelForge 相对优势：**

- 已有 canon revision、source provenance、generation audit 和工具权限边界。
- 可把上述功能升级为带可视化证据链的审核工作流，而不是只做文本建议。

### 云音小说工厂：模块级模型绑定与明确的草稿/正史边界

仓库：<https://github.com/ZIO-YBFH/yunyin-novel-factory>

公开状态：约 6 Stars；Tauri、React、TypeScript、SQLite；主要面向本地 Windows。

它把小说定位、设定生成、大纲、草稿、质检、正史入库和记忆更新分成独立步骤，并明确“草稿不污染正史、未确认记忆不入账”。

**可借鉴：**

- 每个创作模块可绑定独立模型和参数：定位、设定、大纲、续写、质检、记忆提取。
- 章节状态机可体现：草稿生成、质检、人工修改、正史入库、记忆更新。
- 结构化模块必须容忍模型坏 JSON：显示原始响应、允许修正、绝不静默写库。
- 导出时明确排除草稿、API Key、日志、prompt 和模型响应。
- Provider 支持多个兼容接口，并用双阶段连接测试处理不支持模型列表的服务商。

**NovelForge 落地点：**

- 在现有 Generation、Analysis 和 Proposal 模型上补一个可见的章节生命周期状态。
- 在设置中支持按 task profile 配置 Provider 和模型。
- 分离“文本草稿”和“结构化提案”，避免一个屏幕同时承载。

### Manong Novel：完整首次旅程和沉浸式阅读

仓库：<https://github.com/qq1171910065/manong-novel>

公开状态：约 5 Stars；MIT；Electron、Vue；含书架、灵感、蓝图、素材库、写作台、阅读窗口和 TTS。

**可借鉴：**

- 首页是“继续写作”入口，不是功能目录堆砌。
- 使用示例作品完成首次引导：书架 → 蓝图 → 写作 → 阅读。
- 灵感阶段用对话式建议芯片收集方向，而不是一开始就展示复杂表单。
- 素材库中的人物和文风可以跨项目复用，但项目正典仍应隔离。
- 独立阅读窗口、分页导航和朗读可降低成书后的离开感。

**NovelForge 落地点：**

- 首页改为最近项目、最近章节、下一步行动和草稿待审核。
- 创建项目后提供可跳过的“首章引导”。
- 为局部生成和单章阅读提供沉浸模式，但不影响当前版本和保存状态。

### 小说工坊（HadenKai）：Agent 四阶段和可撤销的代改

仓库：<https://github.com/HadenKai/novel-writer>

公开状态：约 2 Stars；MIT；Electron、React、Express、Node；强调离线优先和可撤销 AI 修改。

**可借鉴：**

- 将整章重写拆为构思、起草、自检、修订，分别展示进度和产物。
- 所有代改支持 diff、采用、拒绝和撤销；AI 不直接写正文或正典。
- 支持续写、润色、问题修正、降 AI 痕迹等独立任务，而不是只有一个巨大的“生成”按钮。
- 可按上下文预算裁剪提示词，并向用户显示模型、token/成本和来源（若 Provider 暴露）。
- 离线测试使用临时数据目录，避免真实用户数据参与自动化测试。

**NovelForge 落地点：**

- 在 Editor 工具栏增加结构化任务菜单：续写、改写选区、润色、critique、依据大纲写。
- 为 generation 记录单独的阶段日志和 diff，而不是只记录最终文本。
- 正文生成和正典提案都应支持撤销及审计记录。

## 4. 值得借鉴的非竞品工具

以下工具不是当前调研的主目标，但在桌面体验、结构化文本和发布工作流上仍有参考价值：

- **Joplin**：文件夹、标签、同步、插件、导出和可恢复删除，可借鉴本地数据的可靠性与备份体验。
- **Obsidian**：双向链接、关系图、局部搜索、插件生态可借鉴正典关系和知识工作台，但不能让普通作者承担“维护图谱格式”的成本。
- **Scrivener**虽然不是开源，但有成熟的 binder、corkboard、章节集合、快照和 compile 发布流程；可借鉴信息架构和成书编排，不必照抄商业定价与产品形态。
- **Zettlr**：引用、写作统计、项目导出和学术工作流，可借鉴文稿与附件的管理方式。
- **Sigil**：EPUB结构、目录、校验和成书导出，可借鉴项目→章节→成书的发布管线。

## 5. 按优先级列出的建议

### P0：立即进入产品与交互设计

1. **项目初始化向导**
   - 使用 premise、题材、目标读者、主角、冲突、世界规则、首章目标。
   - 所有 AI 草案都进入 review queue，作者逐项确认。

2. **章节工作台三栏布局**
   - 左：卷/章/场景结构和状态。
   - 中：稿纸编辑器，保留 rich text/Markdown 切换。
   - 右：AI助手、相关正典、来源、章节历史。

3. **章节状态机**
   - `draft → review → canon → exported`。
   - 草稿、正史、分析建议和记忆更新使用独立状态，页面上明确标注来源。

4. **正典审核面板**
   - 显示原值、新值、证据、影响范围和置信度。
   - 支持逐条 approve/reject，保留拒绝原因和修订历史。

5. **上下文可解释性**
   - AI 对话和续写显示使用了哪些章节、人物、设定和版本。
   - 每次生成记录 task profile、provider、模型、context sources 和结果。

### P1：形成成熟长篇工作流

1. 从 premise 到多层概要再到章节大纲。
2. 索引卡视图和时间线视图，支持拖拽重排和设置故事时间。
3. 人物冲突、目标、恐惧、秘密、关系有效区间和人物状态快照。
4. 叙事线、伏笔、计划回收章、世界规则和关键事件。
5. 独立阅读模式、全书搜索、分页、字数统计和成书导出。
6. 多版本生成并排预览，支持局部采纳和完整撤销。
7. 写作 Agent 分阶段：构思、起草、自检、修订；阶段失败不覆盖正文。

### P2：差异化增强

1. 可复用的文风样本库、人物模板和项目模板。
2. 本地小模型的保守上下文模式，按预算裁剪提示词。
3. 全书节奏和章目标分析：开场钩子、冲突、悬念、结尾承诺。
4. 项目健康仪表盘：连续性风险、未回收伏笔、人物状态冲突、长期未更新设定。
5. 可选关系图与故事线，但应由结构化数据生成，不要求作者手工维护图形布局。

## 6. 不建议的方向

- 不做一个按钮生成整本书，且不把整本生成结果直接落为正史。
- 不把聊天历史当作长期记忆的唯一来源。
- 不把人物和关系放成自由文本字段后再用模型猜测，结构化字段和证据来源更重要。
- 不把 Provider Key、日志、prompt 和草稿混进项目导出。
- 不强迫作者先理解向量检索、嵌入、Agent、MCP 等技术概念。
- 不为了国内网文或复杂世界观而牺牲通用长篇小说场景。
- 不把商业工具的名家文风、人物 IP 或受版权保护文本直接移植到开源版本。

## 7. 最适合当前 NovelForge 的最小闭环

建议先实现以下四个页面或工作流，而不是继续横向堆功能：

```text
项目概览
  -> 创建向导与默认结构
  -> 大纲与人物正典
  -> 章节稿纸 + 上下文来源
  -> AI 草稿预览与采纳
  -> 自动分析提案
  -> 作者逐条审批正典
  -> 章历史/回滚
  -> 项目导出与成书导出
```

界面上应始终回答作者最常问的四个问题：

1. 我现在在哪一章、这一章的目标是什么？
2. 这次 AI 使用了哪些当前设定和章节来源？
3. 哪些变化只是草案，哪些已经成为正典？
4. 我下一步应该写、改、审核还是导出？
